Section 03 · Severity P0

Blockers

Each of these causes a guaranteed store rejection or a functionally broken app. All eleven must close before either submission.

P0-1No way to delete an account — violates both stores

There is no account-deletion feature anywhere in the product. Verified: zero matches across frontend/app, frontend/components, frontend/services, and no delete-account route in backend/routes — the only router.delete handlers cover individual trades.

  • PLAY · USER DATA Any app allowing account creation must offer in-app deletion and a publicly reachable web deletion URL declared in Play Console → Data safety. edgecipline.com/delete-account currently returns 404.
  • APPLE · 5.1.1(v) Apps supporting account creation must let users initiate deletion from within the app.
Fix → Add DELETE /api/profile/account (hard-delete or anonymise User, Trades, Reflections, Checklists, device tokens, Cloudinary uploads and the Firebase Auth user), a confirm-flow entry in app/profile/page.js, and a public /delete-account web page describing the process.
P0-2A fake payment form ships inside the release build

components/SmartPaywall.js is live and mounted in app/upload-trade/page.js:317. Its checkout loader branches on platform:

// SmartPaywall.js:26
function isSandboxCheckout() {
  return isNativeAndroidApp() || !String(process.env.NEXT_PUBLIC_RAZORPAY_KEY_ID || "").trim();
}

Two separate failures fall out of that one line:

On Android — the check is true, so the app injects utils/mockRazorpay.js: a full-screen imitation Razorpay checkout with card-number, expiry and CVV inputs, a "Pay" button and a "simulate failure" button. It grants a paid subscription with no transaction. Confirmed present in the shipped bundle. PLAY · DECEPTIVE BEHAVIOR + PAYMENTS Rejection, with app-suspension risk.

On iOS — the platform check is false and the Razorpay key is non-empty, so the sandbox branch is skipped and the app loads the real checkout.razorpay.com/v1/checkout.js. APPLE · 3.1.1 Digital subscriptions must use In-App Purchase; a third-party processor is an automatic rejection. It would also fail at runtime — the key is a placeholder.

Fix → Pick one strategy; do not ship the current hybrid. (a) Recommended for v1: remove the paywall from both mobile builds. Sell on the web only and have the app read subscription status — Apple 3.1.3(b) Multiplatform permits honouring a subscription bought elsewhere, provided the app contains no purchase UI and no link to buy. (b) Implement Google Play Billing + StoreKit properly (weeks, not days). Either way, delete utils/mockRazorpay.js from production builds entirely — a fake payment screen must never be in a store artifact.

P0-3"Upgrade Plan" button leads to a 404 inside the app

app/profile/page.js:349 renders a prominent gradient CTA:

{profile?.subscriptionStatus !== "active" && (
  <Link href="/pricing">Upgrade Plan →</Link>

There is no /pricing route — not in frontend/app/, and no out/pricing* in the static export. Every user whose subscription is not active — which includes every fresh reviewer account — taps this and gets a 404 screen.

APPLE · 2.1 APP COMPLETENESSPLAY · BROKEN FUNCTIONALITY Near-certain rejection on first review.

Fix → Remove the CTA (per P0-2a) or build the route. Then sweep for other dead links — app/admin/users/page.js:49 also deep-links to /pricing.
P0-4The release bundle is baked against the staging API

frontend/.env.local line 1 sets NEXT_PUBLIC_API_URL=https://staging-api.stratedge.live/api.

output: "export" compiles that string into the JS chunks — verified present in out/, android/app/src/main/assets/public and ios/App/App/public. npm run android:build reads the same file, so today's release AAB ships pointing at staging.

The guard meant to catch this has been widened to let it through:

// config/environment.js:5
const PRODUCTION_API_HOSTS = new Set(["api.stratedge.live", "staging-api.stratedge.live"]);

The comment three lines above literally reads "Never point a release build here" — but nothing enforces it.

Fix → Add a .env.production pinned to api.stratedge.live, and gate the staging host behind a non-production mode so a production build physically cannot resolve it.
P0-5Placeholder Razorpay key passes production validation

.env.local sets NEXT_PUBLIC_RAZORPAY_KEY_ID=rzp_live_placeholder. The validator at config/environment.js:127 only checks startsWith("rzp_live_"), and hasPlaceholder() at line 44 only matches ^(your_|replace_|example|changeme|<). The value sails through both.

So the "production requires a live key" control is defeated — and combined with P0-2, the iOS build would load a real Razorpay SDK holding a dead key.

Fix → Add placeholder|dummy|test|sample to hasPlaceholder() and enforce a minimum key length.

P0-6The full admin console ships inside the consumer app

Both mobile bundles contain the complete internal back-office:

android/app/src/main/assets/public/admin/{login, dashboard, users, payments,
                                          trades, monitoring, feedback, issues, expired-users}
ios/App/App/public/admin/...          (identical)

A reviewer — or any user — can navigate to /admin/login inside the app. admin/users exposes subscription activation/deactivation; admin/payments exposes revenue.

APPLE · 2.3.1 HIDDEN FEATURES Apple explicitly rejects for this. It is also an unnecessary attack surface — the auth check lives in admin/layout.js, which is client-side.

Fix → Exclude app/admin/** from the Capacitor export (separate build target, or a build-time route filter) and ship admin as a web-only deployment.
P0-7iOS: Firebase is not configured — Google Sign-In is dead
  • ios/App/App/GoogleService-Info.plist — missing
  • AppDelegate.swift — never calls FirebaseApp.configure()
  • Info.plist has no CFBundleURLTypes with the REVERSED_CLIENT_ID scheme

@capacitor-firebase/authentication is the only sign-in path with a configured provider (google.com). On iOS it will fail or crash on first tap.

Fix → Register the iOS app in the Firebase console, add GoogleService-Info.plist to the Xcode target, call FirebaseApp.configure(), and add the reversed-client-ID URL scheme.
P0-8iOS: no privacy manifest (PrivacyInfo.xcprivacy)

Required by Apple since May 2024 for apps using "required reason" APIs. Capacitor core uses UserDefaults; the app also touches file timestamps and disk space. Submitting without it produces ITMS-91053: Missing API declaration and the build is rejected at upload.

Fix → Add PrivacyInfo.xcprivacy to the App target declaring at minimum NSPrivacyAccessedAPICategoryUserDefaults (reason CA92.1), plus your data-collection types: email, name, user content, crash data, device ID.

P0-9iOS: missing camera / photo usage descriptions → guaranteed crash

The app uploads trade screenshots — Android declares CAMERA and READ_MEDIA_IMAGES (AndroidManifest.xml:91-97). Inside a WKWebView, <input type="file" accept="image/*"> triggers the iOS camera and photo picker.

Info.plist contains no NSCameraUsageDescription and no NSPhotoLibraryUsageDescription. iOS terminates the app immediately when a permission is requested without its string, and the binary is rejected at upload (ITMS-90683).

Fix → Add both keys with honest, specific copy, e.g. "Edgecipline uses your camera to capture broker screenshots so trades can be logged automatically."
P0-10iOS: push notifications cannot work

@capacitor/push-notifications is a dependency and appears in packageClassList, but:

  • there is no App.entitlements file → no aps-environment key → APNs registration fails and Xcode blocks the upload
  • AppDelegate.swift does not forward the registration callbacks the Capacitor plugin requires
  • no APNs auth key uploaded to Firebase (required for FCM → APNs)
func application(_ application: UIApplication,

func application(_ application: UIApplication,
    didFailToRegisterForRemoteNotificationsWithError error: Error) {

P0-11The public Privacy Policy URL is broken

Both consoles require a live, publicly reachable privacy policy URL, and Play flags the listing if it ever stops resolving.

Section 04 · Severity P1

High — rejection risk, or breaks on launch day

These will not necessarily stop the first review, but each one either invites a policy question or silently breaks the app in production.

P1-1Signing key is compromised, and the artifacts are still tracked

The June report claimed these were "staged for untracking." They remain tracked today: frontend/android.zip (21 MB) and frontend/android/app/build/outputs/apk/debug/app-debug.apk.

android.zip contains google-services.json, local.properties, a debug APK and the old plaintext signing properties, and is still in git history (commit 6beeccd).

Fix → git rm --cached both, rotate the upload key, then git filter-repo before the repo is ever shared.
P1-2Google Sign-In will break the day you publish

google-services.json registers exactly one Android OAuth client (cert hash 2c2e3202…). Play App Signing re-signs your AAB with Google's key, so the installed app's SHA-1 will not match anything in Firebase.

Fix → After the first upload, copy the App signing key certificate SHA-1 from Play Console → Setup → App integrity into Firebase, re-download google-services.json, and rebuild. Add the upload-key SHA-1 too.

P1-3 SCHEDULE_EXACT_ALARM needs a Play declaration AndroidManifest.xml:108. On API 34+ this is revoked by default, and Play restricts it to alarm-clock/calendar apps via a sensitive-permission form. A trading-checklist reminder is unlikely to qualify. Drop it and rely on the WorkManager fallback already implemented.

Recommended order of work

Sequenced so the longest calendar dependencies start on day one and code work runs in parallel behind them.

Start today, before any code: open the Play Console account, complete identity verification, and begin the 14-day / 20-tester closed test. It is the longest pole in the schedule and it is pure waiting — every day you delay it is a day added to launch.

  1. Delete mockRazorpay.js; strip the paywall and /pricing CTA from mobile builds P0-2, P0-3
  2. Build account deletion end to end: API, profile UI, public web page P0-1
  3. .env.production with the prod API; remove staging from the prod allowlist; tighten hasPlaceholder() P0-4, P0-5
  4. Exclude app/admin/** from the Capacitor export P0-6
  5. Redeploy the website; fix /privacy-policy, /support, /delete-account P0-11
  6. Untrack android.zip and app-debug.apk; rotate the upload key P1-1
  7. Drop SCHEDULE_EXACT_ALARM and FOREGROUND_SERVICE; wire versionCode to CI P1-3, P1-5, P1-6
Week 2Android submission + iOS setup
  1. Add the Play App Signing SHA-1 to Firebase; verify Google Sign-In on a Play-signed internal build P1-2
  2. Self-host fonts P2-1
  3. Decide the com.edgecpline question — now or never P2-2
  4. On a Mac: pod install, Firebase iOS config, PrivacyInfo.xcprivacy, usage-description strings, push entitlement + AppDelegate callbacks, deployment target, arm64, signing P0-7 → P0-10, P1-7
Week 3iOS QA and submission
  1. Full device pass on iOS: sign-in, camera upload, push, offline, deep links
  2. Screenshots, listing copy, demo account, App Privacy label
In one line

The engineering foundation is solid, but the app is not shippable in its current state — a mock payment screen and a dead upgrade button would fail review on their own, account deletion is legally mandatory and entirely absent, the bundle points at staging, and the iOS target has never been configured or compiled. Fix the eleven P0s and Android is a realistic one-week submission; iOS needs a Mac and roughly three.
